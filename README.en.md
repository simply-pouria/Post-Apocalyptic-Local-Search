# Part One — Helper Functions

In the first stage, several helper functions were added to the class so that the code could obtain the information it needed from the environment. This information includes the number of rows and columns in the environment, the maximum number of allowed sensors, sensor range, target positions, and whether a cell is valid. The code was also written to remain compatible if the project environment uses different names for the same parameters. For example, if the maximum number of sensors is defined as either `sensors_max` or `max_sensors`, both forms are supported. The same approach is used for sensor range, supporting both `range_sensor` and `sensor_range`.

The `evaluate(state)` function was implemented as the cost function. It determines how suitable a sensor configuration is. In this design, a lower cost indicates a better state. The most important factor in the cost is the number of targets that are not covered by any sensor. Therefore, leaving a target uncovered adds a large penalty to the cost, encouraging the algorithms to move toward configurations that cover more targets.

In addition to target coverage, the number of sensors used is also included in the cost function. A small cost is added for each sensor so that, when possible, the algorithm prefers solutions that use fewer sensors. Thus, if two configurations provide approximately the same coverage, the one that achieves it with fewer sensors is evaluated more favorably. A small penalty is also added for redundant coverage: if multiple sensors unnecessarily cover the same target, the cost increases slightly.

To prevent invalid states from being generated or accepted, the evaluation function assigns large penalties to important violations. If a sensor is outside the environment, placed on an obstacle, duplicated at the same position as another sensor, or if the number of sensors exceeds the allowed maximum, the cost of that state increases sharply. This encourages the algorithms to move away from invalid states and toward acceptable configurations.

The `initialize_state()` function was implemented to create a valid initial state. It randomly selects positions for sensors, but before adding each position it checks that the cell is valid, is not an obstacle, is not duplicated, and does not cause the total number of sensors to exceed the allowed limit. As a result, the algorithms begin with an acceptable configuration rather than entering the search process from an invalid state.

The `get_neighbor(state)` function was implemented to generate a neighboring state from the current state. Three main types of changes are considered: moving an existing sensor, adding a new sensor, and removing an existing sensor. For a move operation, one sensor is selected and relocated to another valid cell. For an add operation, if the maximum number of sensors has not yet been reached, a new sensor is placed at a valid position. For a remove operation, one existing sensor is deleted from the configuration.

Using these three operations makes the search space more flexible. If only sensor movement were allowed, the number of sensors would remain constant. By also supporting addition and removal, the algorithm can explore configurations containing different numbers of sensors. This is important for balancing coverage quality against efficient resource usage.

State-validation logic was also added. It checks that no sensor is outside the environment, no sensor is placed on an obstacle, no duplicate positions exist, and the number of sensors does not exceed the maximum. A cleanup function was also written to remove invalid or duplicate positions before neighbor generation. This makes the search process more stable and reliable.

At this point, the class can evaluate sensor configurations, construct a valid initial state, generate neighboring states, enforce environment constraints, and support moving, adding, and removing sensors. These changes provide the foundation required to run local-search algorithms such as Hill Climbing and Simulated Annealing.

# Part Two — Random-Restart Hill Climbing

In this section, `Random-Restart Hill Climbing` was implemented. The main difference from ordinary `Hill Climbing` is that the algorithm does not begin from only one initial state; instead, it runs multiple times from different initial states. During each run, like standard Hill Climbing, the algorithm accepts only a neighbor with a lower cost. Each individual run is therefore still greedy, but using multiple random starting points reduces the chance of becoming trapped in a weak solution. This implementation is simpler than stochastic hill climbing and, according to the class discussion, also performs better.

The main parameters are `restarts`, `max_iterations`, and `max_no_improve`. `restarts` determines the number of independent runs. A larger value allows the algorithm to explore more regions of the search space, but also increases execution time. `max_iterations` defines the overall search budget, while `max_no_improve` determines how many consecutive iterations without improvement are allowed before the current restart is terminated and the algorithm begins again from a new point.

The main problem with ordinary `Hill Climbing` is that it can become trapped in a `Local Optimum`: a state in which no nearby neighbor is better even though better solutions exist elsewhere in the full search space. With `Random-Restart`, if one run stops at such a point, later runs begin from new random states. This provides a simple way to reduce the local-optimum problem without, as in `Simulated Annealing`, probabilistically accepting worse states.

The behavior of this algorithm on different maps depends on the distribution of targets, the number of obstacles, sensor range, and the value of `sensors_max`. On simpler maps, a small number of restarts is usually enough to find a good solution. On more complex maps with many obstacles or widely separated targets, increasing the number of restarts can help the algorithm try more distinct configurations. Overall, this method is more robust than ordinary `Hill Climbing`, although it has a higher computational cost.

# Part Three — Simulated Annealing

The main idea of this method is inspired by the physical annealing process of metals. Just as a hot metal is cooled gradually so that its atoms settle into a stable configuration, the algorithm initially explores the search space with substantial freedom and gradually becomes more greedy over time. The main difference from `Hill Climbing` is that the algorithm sometimes accepts states with a higher cost in order to avoid becoming trapped in local optima.

The algorithm was implemented directly according to the standard textbook pseudocode. At each step, a random neighbor of the current state is selected and `ΔE = cost(current state) − cost(neighbor)` is computed. If `ΔE > 0`, the neighbor has a lower cost and is accepted unconditionally. If `ΔE ≤ 0`, the neighbor is worse and is accepted with probability `e^(ΔE/T)`. At high temperatures, this probability is close to 1 and almost any state may be accepted; as the temperature gradually decreases, the probability approaches zero.

An exponential schedule is used to reduce the temperature: `T(t) = T₀ × α^t`. The algorithm stops when the temperature falls below `T_min` or when the number of iterations reaches the specified maximum. The main parameters are `T₀ = 500`, `α = 0.995`, and `T_min = 0.01`. The initial temperature of 500 was chosen because a typical move that causes one target to become uncovered changes the cost by approximately 50 units. At this temperature, the probability of accepting such a move is `e^(-50/500) ≈ 0.90`, which allows substantial exploration early in the search. The cooling rate `α = 0.995` is also slow enough to provide broad exploration while allowing the algorithm to behave more like greedy hill climbing in its later stages.

The main advantage over `Hill Climbing` is the ability to escape local optima. In Hill Climbing, whenever the algorithm reaches a point with no better neighbor, it stops even if that point is not the global optimum. In `Simulated Annealing`, these points are only temporary obstacles that can be crossed with a certain probability. As a result, the algorithm generally finds better solutions than ordinary `Hill Climbing`, although compared with `Random-Restart Hill Climbing` the difference is not substantial and the computational cost is higher.

The behavior of this algorithm on different maps depends strongly on the chosen parameters. On simple maps, a lower initial temperature and faster cooling are sufficient. On complex maps with many obstacles or dispersed targets, keeping the temperature high for longer gives the algorithm more opportunity to try diverse configurations. Overall, `Simulated Annealing` is the most flexible single-state algorithm in this project: it is neither completely greedy like `Hill Climbing` nor directionless like pure random search, but instead balances the two through controlled temperature reduction.

# Part Four — Local Beam Search

In this section, `Local Beam Search` was implemented as a score-based algorithm. Its main difference from `Hill Climbing` is that it maintains multiple current states simultaneously rather than only one. The number of these states is determined by the `beam_width` parameter. At each iteration, neighbors are generated from every state in the beam, all candidates are evaluated, and the best few states are retained for the next iteration.

The main parameters are `beam_width`, `neighbors_per_state`, `max_iterations`, and `max_no_improve`. `beam_width` determines how many sensor configurations are maintained at the same time. A larger value usually improves search quality but increases the number of evaluations and the execution time. `neighbors_per_state` determines how many neighbors are generated from each state. If this value is too small, search diversity decreases; if it is large, the algorithm becomes slower.

With respect to the `Local Optimum` problem, this algorithm performs better than ordinary `Hill Climbing` because it does not depend on a single path. If one state in the beam enters a weak region, the other states can still follow better paths. However, `Local Beam Search` does not guarantee finding the global optimum. If the beam states gradually become too similar, search diversity decreases and the algorithm may converge prematurely.

The behavior of this algorithm on different maps generally depends on `beam_width` and map complexity. On small maps, a narrow beam is sufficient and the algorithm quickly reaches a suitable solution. On larger maps, or maps with widely dispersed targets, a wider beam can be useful because several different sensor configurations are examined simultaneously. Compared with `Random-Restart Hill Climbing`, this method follows several paths in a single run instead of performing multiple independent runs. Therefore, when the parameters are chosen appropriately, it can search more broadly, although it requires more memory and time. In my runs, it performed approximately as well as Random-Restart Hill Climbing.

# Part Five — Tabu Search

In this section, `Tabu Search` was implemented as a score-based algorithm. The main idea is to combine local search with short-term memory. Unlike `Hill Climbing`, which stops as soon as it reaches a local optimum, this algorithm continues searching even if it cannot find a better neighbor. To avoid cycling within one region, however, recently performed moves are stored in a tabu list and are temporarily prevented from being repeated.

The main parameters are `max_iterations`, `tabu_tenure`, `neighbors_per_iter`, `max_no_improve`, and `max_no_improve_restart`. `tabu_tenure` determines how many iterations each move remains in the tabu list. If the value is too small, the algorithm can return to the same paths; if it is too large, the search space becomes overly restricted. `neighbors_per_iter` specifies how many neighbors are examined at each iteration in order to select the best non-tabu move.

One problem with a tabu list is that the best available move may sometimes be tabu. To address this, an `Aspiration Criterion` is used. Under this criterion, if a move is tabu but would produce a new best overall cost, the tabu restriction is ignored and the move is accepted. This prevents the algorithm from missing an excellent solution merely because of an artificial restriction.

If the algorithm goes for `max_no_improve_restart` consecutive iterations without improving the best overall cost, the current state is replaced with a completely random state and the tabu list is cleared. This mechanism is similar to restarting in `Random-Restart Hill Climbing`, except that the best overall solution found so far is preserved and only the search's current starting point is changed.

The behavior of this algorithm on different maps depends on the lifetime of entries in the tabu list and on the size of the examined neighborhood. On maps where targets are concentrated, the algorithm can quickly enter a good region of the search space and the tabu list prevents it from returning to previous states. On more complex maps, the diversification mechanism becomes more important. Compared with `Hill Climbing`, this method uses memory to prevent aimless cycling, but it requires more time to examine neighbors at each iteration. Overall, `Tabu Search` performs best on problems whose neighborhoods have a regular structure.

# Part Six — Genetic Algorithm

In this section, the `Genetic Algorithm` was implemented as a score-based algorithm. This algorithm works with a population of states rather than a single current state. The main idea is inspired by natural evolution: better states have a greater chance of reproducing, combining features from two good parents can produce a better child, and random mutations maintain population diversity.

The chromosome representation in this implementation is a fixed-length list of size `max_sensors`. Each position in the list either contains a tuple `(row, col)`, representing a sensor at that position, or contains `None`, meaning that the slot is empty. This encoding makes crossover possible between chromosomes of equal length and removes complications caused by variable-length representations. After each operation, a repair function corrects duplicate and invalid positions.

The main parameters are `pop_size`, `max_generations`, `crossover_rate`, `mutation_rate`, `tournament_size`, and `elitism_count`. `pop_size` determines the population size: a larger population provides more diversity but increases the time required for each generation. `crossover_rate` controls the probability of crossover, and `mutation_rate` determines the probability that mutation is applied to each individual. `elitism_count` specifies how many of the best individuals in each generation are transferred directly to the next generation.

Tournament selection is used to choose parents. A specified number of individuals are selected randomly from the population, and the one with the best cost is chosen as a parent. This method is more stable than roulette-wheel selection and does not require cost values to be normalized. Uniform crossover is used: for each chromosome position, a 50% probability independently determines whether the gene comes from the first or second parent. Mutation behaves similarly to the neighbor-generation function and randomly performs one of three operations: moving, adding, or removing a sensor.

The main disadvantage of the `Genetic Algorithm` compared with single-state methods is its higher computational cost, because every individual in the population must be evaluated in each generation. Its main advantage, however, is its ability to explore multiple regions of the search space simultaneously. Combining features from two strong configurations through crossover can produce configurations that are better than either parent, which is not possible in single-state algorithms.

The behavior of this algorithm on different maps depends on population size and the number of generations. On small maps, a small population and a limited number of generations are sufficient. On larger maps, where the search space is broader, a larger population and more generations can lead to better configurations. Overall, this algorithm is more suitable for problems with very large search spaces and, with appropriate parameter tuning, can outperform all other algorithms in this project, although it also requires more execution time.
